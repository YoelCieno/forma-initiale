## Behavior Specs

### Requirement: Consumer template without override boilerplate

The shell ProductsPage SHALL render product cards through a wrapper element with a single typed input — no `ngComponentOutlet`, `cardInputs()`, or registry import at the consumer.

#### Scenario: Shell template shape

- GIVEN the white-label ProductsPage
- WHEN the product grid renders
- THEN each grid child is `<product-card [product]="product" />`
- AND the ProductsPage template contains no `ng-container`/`ngComponentOutlet`/`cardInputs()`

### Requirement: Wrapper resolves override through registry

The wrapper SHALL resolve its rendered class via `injectComponentOverride('product-card', ProductCard)` — same accessor as today.

#### Scenario: No override → shell default

- GIVEN the `COMPONENT_OVERRIDES` registry is empty
- WHEN the wrapper renders
- THEN an `app-product-card` host is present (shell ProductCard)

#### Scenario: Tenant override → tenant card

- GIVEN `componentOverrides: { 'product-card': FpProductCard }` is registered
- WHEN the wrapper renders
- THEN an `fp-product-card` host is present
- AND no `app-product-card` host is present

### Requirement: Input forwarding

The wrapper SHALL forward the `product` object to the dynamic component via `ngComponentOutletInputs` using one mapping site inside the wrapper.

#### Scenario: Inputs reach the card

- GIVEN a `ProductView` with title, price, rate
- WHEN the wrapper renders with `[product]`
- THEN the inner card receives matching title/price/rate values

### Requirement: Layout parity

The wrapper SHALL NOT alter grid layout — inner card remains the effective grid item.

#### Scenario: Grid child positioning

- GIVEN the products grid uses `grid-template-columns` auto-fill
- WHEN wrappers are inserted as grid children
- THEN wrapper host uses `display: contents`
- AND layout matches pre-wrapper rendering (visual parity)
